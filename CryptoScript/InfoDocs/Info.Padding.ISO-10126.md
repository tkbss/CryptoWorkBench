# PADDING ISO-10126

`ISO-10126` is the canonical CryptoScript name for padding that records the total padding length in the final byte. CryptoScript fills the preceding padding bytes with cryptographically random values.

---

## Syntax

Use the canonical, case-sensitive literal `ISO-10126` as the value of `#PAD`:

```text
#PAD:ISO-10126
```

The spelling `ISO10126` is not a registered CryptoScript padding value.

## CryptoScript Padding Rule

For a block size `B` and an input length `L`, both measured in bytes, the number of padding bytes is:

```text
N = B - (L mod B)
```

CryptoScript appends `N - 1` cryptographically random bytes, followed by one byte with the numeric value `N`. Therefore, `1 <= N <= B`, and the padded length is always a positive multiple of the block size.

Each random filler byte may contain any value from `0x00` through `0xFF`; `0x00` is not excluded. Only the final length byte has a structurally fixed value.

## Random Filler Bytes and Determinism

When `N > 1`, the padding contains at least one random filler byte. Encryptions with the same key, IV, and plaintext can therefore produce different ciphertexts. Repetition remains possible and is not excluded by randomness.

When `N = 1`, there are no random filler bytes and the padding consists only of `0x01`. With a fixed key, IV, and plaintext, this particular padding case is deterministic.

## Full Block and Empty Input

ISO-10126 always adds padding:

- For AES with a 16-byte block, an aligned or empty input receives fifteen random bytes followed by `0x10`.
- For DES3 with an 8-byte block, an aligned or empty input receives seven random bytes followed by `0x08`.

Thus an already block-aligned input receives one complete additional padding block. The AES behavior is CryptoScript/.NET behavior; the historical ISO 10126-2 specification describes DEA with 8-byte blocks in CBC mode.

## Unpadding and Validation

CryptoScript reads `N` from the final decrypted byte and requires `1 <= N <= B`. It then removes exactly `N` bytes. The preceding `N - 1` filler bytes are not checked for particular values because this format does not assign them fixed individual values. Fillers such as `0x00`, `0xFF`, `0xA5`, and `0x7C` are equally acceptable when they occur within a padding field of the declared length.

When `N = 1`, there is no filler byte before the length byte. Values such as `N = 0` or `N` greater than the block size are invalid. Empty and non-block-aligned ciphertext are also rejected by the applicable block-cipher paths.

## Supported Mechanisms

`ISO-10126` is selectable and effective for:

- AES-CBC encryption and decryption
- DES3-CBC encryption and decryption
- DES3-ECB encryption and decryption

It is not the default padding for these mechanisms; AES-CBC, DES3-CBC, and DES3-ECB default to `PKCS-7`.

DES3-CBC-MAC explicitly rejects ISO-10126, and DES3-RETAIL does not support it. AES-ECB always uses `NONE`; AES-CMAC and DES3-CMAC do not use external ISO-10126 padding; and AES-CTR, AES-GCM, AES-CCM, and AES-GMAC do not apply effective external ISO-10126 padding.

## Example Usage

### Byte-Level Example

For a 16-byte AES block:

```text
Input:   00 01 02 03 04 05 06 07 08 09 0A 0B 0C
Padding: ?? ?? 03
Result:  00 01 02 03 04 05 06 07 08 09 0A 0B 0C ?? ?? 03
```

Each `??` represents a cryptographically random byte generated by CryptoScript between `00` and `FF`. The two bytes need not differ and may be `00`; the structurally guaranteed suffix is `?? ?? 03`, not particular filler values.

### CryptoScript Example

```cryptoscript
KEY k = GenerateKey(AES-CBC,0x(2B7E151628AED2A6ABF7158809CF4F3C))
PARAM p = Parameters(#MECH:AES-CBC,#IV:0x(000102030405060708090A0B0C0D0E0F),#PAD:ISO-10126)
VAR input = 0x(010203)
VAR ciphertext = Encrypt(p,k,input)
VAR decrypted = Decrypt(p,k,ciphertext)
```

The resulting `ciphertext` contains 16 bytes, and `decrypted` is `0x(010203)`. Because the padding contains random filler bytes, the ciphertext can differ between executions.

## Historical and Source Note

ISO 10126-1:1991 is titled *Banking — Procedures for message encipherment (wholesale) — Part 1: General principles*. ISO 10126-2:1991 is titled *Banking — Procedures for message encipherment (wholesale) — Part 2: DEA algorithm*. Both standards were later withdrawn.

Section 6 of ISO 10126-2:1991 defines the octet-padding field for the historical DEA/CBC context. It permits arbitrary contents in the filler octets and records the total padding length in the final octet; it does not require cryptographically random filler. CryptoScript uses the corresponding .NET byte format for its supported AES-CBC, DES3-CBC, and DES3-ECB paths. In .NET, the filler bytes are generated with `RandomNumberGenerator.Fill`, which is the source of CryptoScript's concrete random-filler behavior.

The foreword of ISO 10126-2:1991 records a historical relationship with ANSI X9.23:1988. This does not make CryptoScript's `ISO-10126` and `ANSI-X923` modes identical: CryptoScript uses random filler for the former and zero-valued filler for the latter.
