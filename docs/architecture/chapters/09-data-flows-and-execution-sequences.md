## 9.1 Scope

A submission, an editor revision and a service job have different boundaries. A submission is one parse unit. A whole-editor job can include many units. The registry owns the job from admission through finalization. The following sequences explain how errors and cancellation affect already published state. [Chapter 8](08-interfaces-and-integration.md) defines the identities used in the requests. [E07](../evidence/mcp-a1.md#e07), [E13](../evidence/mcp-a1.md#e13), [E14](../evidence/mcp-a1.md#e14), [E16](../evidence/mcp-a1.md#e16)

## 9.2 Sequential Execution and Partial State

The runner evaluates statements in order. A terminating exception prevents subsequent statements from running. Successful earlier declarations, assignments and external effects retain the guarantees of their individual operations. A failed script can therefore leave a valid, observable partial state. Syntax rejection prevents execution of that parse unit. A later rejected line cannot undo earlier lines of a book. [E15](../evidence/mcp-a1.md#e15), [E16](../evidence/mcp-a1.md#e16), [E24](../evidence/mcp-a1.md#e24)

Some semantic diagnostics, including some error-severity diagnostics, allow evaluation to continue. Diagnostic severity alone cannot determine whether execution stopped. The assigned value can survive a later type error. File operations keep their own publication and cleanup boundaries. The tests `MissingSourceDoesNotRegisterResult`, `PublicationFailureRemovesTemporary` and `CancelBeforePublicationRemovesTemporary` specify these local guarantees. [File operation tests](https://github.com/tkbss/CryptoWorkBench/blob/8c58e2bd564280b71412cfd6ed9997688bd0bde4/CryptoScriptUnitTest/FileEncryptionTests.cs). [E15](../evidence/mcp-a1.md#e15), [E24](../evidence/mcp-a1.md#e24)

## 9.3 From Execution to GUI Presentation

For an interactive submission the host obtains admission, resets syntax state, parses and awaits the runner. The pipeline waits for outstanding password callbacks, preserving host admission and Core ownership, then copies diagnostics in order. Under `InterpreterExecution.AccessState` it captures the actual runner-visible variables. A capture can succeed after script failure. [E15](../evidence/mcp-a1.md#e15), [E16](../evidence/mcp-a1.md#e16), [E18](../evidence/mcp-a1.md#e18)

The interactive presenter applies a valid snapshot even on script failure. It preserves the identity relationship between the copied runner diagnostic and the exception diagnostic, so the status view appends the exception only if it was not already transported. Distinct diagnostics with identical text retain their order. If capture fails, the GUI keeps its prior variables and marks them stale. If applying a valid capture fails, the collection may already have changed. The presenter reports the failure without appending diagnostics a second time. Successful authorized refresh can clear the stale marker. [Status presentation](https://github.com/tkbss/CryptoWorkBench/blob/8c58e2bd564280b71412cfd6ed9997688bd0bde4/CryptoWorkBenchAvalonia/ViewModels/StatusViewModel.cs) · [Variable presentation](https://github.com/tkbss/CryptoWorkBench/blob/8c58e2bd564280b71412cfd6ed9997688bd0bde4/CryptoWorkBenchAvalonia/ViewModels/VariableViewModel.cs). [E16](../evidence/mcp-a1.md#e16), [E18](../evidence/mcp-a1.md#e18), [E19](../evidence/mcp-a1.md#e19), [E24](../evidence/mcp-a1.md#e24)

Interactive Return can publish anchored output into the editor. A v2 MCP run shares admission and execution, but publishes its bounded result to the registry. It leaves the editor source intact. The dock output pane does not receive those records. Visible variables can remain stale until GUI refresh is permitted after release. [E13](../evidence/mcp-a1.md#e13), [E17](../evidence/mcp-a1.md#e17), [E19](../evidence/mcp-a1.md#e19)

## 9.6 From Snapshot to Edit

The client reads status and a bounded editor snapshot, then acquires control using the instance ID, editor ID and observed revision. A competing operation, changed revision or unavailable registration rejects admission. For an edit the service reserves the host slot and creates an MCP operation ticket on the dispatcher. It validates the requested range, length and insertion boundary, including UTF-16 surrogate pairs and CRLF. [E10](../evidence/mcp-a1.md#e10), [E11](../evidence/mcp-a1.md#e11), [E12](../evidence/mcp-a1.md#e12), [E13](../evidence/mcp-a1.md#e13)

Replacing different text in a nonempty document, or one whose clean state is uncertain, can require local confirmation. After the dialog the service rechecks authority, lease and original ticket before starting the commit. A stale ticket cannot write to a successor document. An identical replacement can finish without a text effect. The final receipt records observed revision, text and history effects, finalization and refresh advice. A failing callback can follow an applied change. Refresh the document and status before choosing a new operation. [E06](../evidence/mcp-a1.md#e06), [E11](../evidence/mcp-a1.md#e11), [E13](../evidence/mcp-a1.md#e13), [E23](../evidence/mcp-a1.md#e23)

## 9.7 From Approval to Execution Result

In the [execution sequence](../diagrams/09-execution.mmd), a new execution ID is scoped to caller source, principal and activation epoch. The service hashes the normalized request, checks the expected editor revision and state version, reserves admission and registers the job. The local dialog identifies the exact script, directory and output policy. Denial rejects the run. If the dialog is unavailable the job can fail. Changing the lease, directory, revision or state across approval can invalidate the request. The worker rechecks its fence before starting a runner. [E13](../evidence/mcp-a1.md#e13), [E14](../evidence/mcp-a1.md#e14), [E23](../evidence/mcp-a1.md#e23)

The whole editor is processed as physical ScriptBook lines. Lines starting with the exact prefix `out:` are skipped. Each executable line is parsed as a unit. Fresh runners use the same variable dictionary. The pipeline awaits desktop password callbacks and records ordered Print/Info and diagnostics at their source. Physical line offsets are preserved for syntax diagnostics. When effects are possible the service advances the state version. Capture failure leaves stale metadata, and recovery recaptures it without rerunning the script. [E13](../evidence/mcp-a1.md#e13), [E15](../evidence/mcp-a1.md#e15), [E16](../evidence/mcp-a1.md#e16), [E17](../evidence/mcp-a1.md#e17)

Losing the request before admission can prevent any job. After admission a cancelled response wait leaves the service-owned task running. The owner may query by execution ID after ordinary lease release. A caller with `execution.run` and the other admission requirements can create a new job and receive its initial reply without `execution.read`. Replaying a retained execution ID or looking up the job later requires the owner to have `execution.read`. Replay returns the filtered result for a matching request fingerprint and a conflict for a different one. Completed results are retained for up to 15 minutes subject to count and byte limits. Eviction leaves an ID tombstone. Returned diagnostics use bounded codes and locations, variables carry metadata, and output text remains subject to approval and grants. [E07](../evidence/mcp-a1.md#e07), [E13](../evidence/mcp-a1.md#e13), [E14](../evidence/mcp-a1.md#e14), [E17](../evidence/mcp-a1.md#e17), [E18](../evidence/mcp-a1.md#e18), [E24](../evidence/mcp-a1.md#e24)

## 9.8 Cancellation, Revocation and Shutdown

A job cancellation receipt records whether the first reason was accepted. Synchronous statements and password or editor callbacks can outlive that request. A late request can leave a completed final statement successful. A job timeout, an expiring editor lease and an expiring session credential affect different owners. STDIO EOF alone leaves the activation intact. [E04](../evidence/mcp-a1.md#e04), [E12](../evidence/mcp-a1.md#e12), [E14](../evidence/mcp-a1.md#e14), [E16](../evidence/mcp-a1.md#e16), [E17](../evidence/mcp-a1.md#e17), [E30](../evidence/mcp-a1.md#e30)

The [recovery paths](../diagrams/09-recovery.mmd) distinguish three completion conditions. **Release** records the end reason and prevents new lease-bound work, while the receipt may still say `Releasing`. **GUI return** requires the original coordinator, settled jobs, callbacks and file/save work, closed native updates and a current successful drain certificate. A detached registration can become unavailable. An uncertifiable native group leaves writes blocked. **Application exit** first defers window close, stops admission, revokes access and joins transport shutdown, service work and inspector transfers. Exit alone tolerates the specifically classified quiescent epoch fault. Other drain failures keep the window protected. Successful exit posts the final close. [E03](../evidence/mcp-a1.md#e03), [E11](../evidence/mcp-a1.md#e11), [E12](../evidence/mcp-a1.md#e12), [E20](../evidence/mcp-a1.md#e20), [E21](../evidence/mcp-a1.md#e21), [E23](../evidence/mcp-a1.md#e23)

Disconnect Codex also invalidates the bearer and issued callers, revokes MCP jobs and their result access, and waits for the original transport and epoch drain. It reports GUI release only after strict certification. The internal lease-only reclaim leaves pairing in place and has no production GUI command. Reconnecting after session-wide disconnect requires a fresh Workbench process. [E03](../evidence/mcp-a1.md#e03), [E08](../evidence/mcp-a1.md#e08), [E12](../evidence/mcp-a1.md#e12), [E21](../evidence/mcp-a1.md#e21), [E23](../evidence/mcp-a1.md#e23)
